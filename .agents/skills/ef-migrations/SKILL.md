# EF Core migrations (PostgreSQL, code-first)

These rules extend `AGENTS.md`. They match the conventions the platform already ships in
`Shipwise.EntityFrameworkCore/Reliability`, so module tables and the shared reliability
tables look the same in the database.

## 1. Ownership and layout

- Each module owns exactly one DbContext, one PostgreSQL database (`shipwise_<module>`,
  lowercase) and one schema (`<module>`, lowercase, e.g. `organizations`). Never map
  another module's tables or reference them with a foreign key; cross-module data moves
  through contracts and messaging.
- Domain entities have no EF references. All mapping is Fluent API in the
  Infrastructure project; no data annotations in Domain.

```
src/Modules/<Module>/
  Shipwise.<Module>.Infrastructure/
    Persistence/
      <Module>DbContext.cs
      <Module>DbContextFactory.cs          design-time factory (see 4)
      Configurations/<Entity>Configuration.cs   one IEntityTypeConfiguration<T> per entity
      Migrations/                          generated by dotnet ef; never written by hand
  Shipwise.<Module>.MigrationRunner/       console app that applies migrations
```

- In `OnModelCreating`: `HasDefaultSchema("<module>")`,
  `ApplyConfigurationsFromAssembly(...)`, and `ApplyReliabilityConfigurations(
  ReliabilityDatabaseProvider.PostgreSql)` only when the module uses outbox, inbox or
  idempotency.
- In `UseNpgsql(...)`: `MigrationsHistoryTable("__EFMigrationsHistory", "<module>")` and
  `MigrationsAssembly` pointing at the Infrastructure project.

## 2. Naming conventions

Identifiers keep EF's PascalCase and are quoted in SQL. Do not add a snake_case
naming-convention package: the reliability check constraints depend on the quoted names.

| Object | Convention | Example |
|---|---|---|
| Database | `shipwise_<module>` | `shipwise_organizations` |
| Schema | lowercase module name | `organizations` |
| Table | PascalCase plural noun, explicit `ToTable(name, schema)` | `"Organizations"` |
| Join table | both names, PascalCase plural | `"OrganizationMembers"` |
| Column | the C# property name | `"DisplayName"` |
| Foreign key column | `<Navigation>Id` | `"OrganizationId"` |
| Primary key | `PK_<Table>` (EF default) | `PK_Organizations` |
| Foreign key | `FK_<Table>_<PrincipalTable>_<Column>` (EF default) | `FK_OrganizationMembers_Organizations_OrganizationId` |
| Index | `IX_<Table>_<Col1>_<Col2>` via `HasDatabaseName` | `IX_Organizations_CreatedAt` |
| Unique index | `UX_<Table>_<Cols>` | `UX_Organizations_Slug` |
| Check constraint | `CK_<Table>_<Rule>` | `CK_Organizations_Status` |
| Migration | Verb-first PascalCase describing the change | `Initial`, `AddOrganizationSlug`, `RenameProjectTitleToName`, `DropLegacyInviteColumns` |

Forbidden migration names: `Update`, `Fix`, `Changes`, `Migration2`, ticket numbers alone,
or anything that does not say what changed. The first migration of a module is `Initial`.

## 3. Column types and mapping rules

| CLR type | PostgreSQL | Rule |
|---|---|---|
| `Guid` id | `uuid` | `ValueGeneratedNever()`; the domain creates ids with `Guid.CreateVersion7()` |
| `DateTimeOffset` | `timestamp with time zone` | Always UTC (`ARCHITECTURE.md`); never `DateTime` |
| `string` | `character varying(n)` | Always `HasMaxLength(n)`; `text` only for genuinely unbounded content, with a comment |
| enum | `smallint` | `HasConversion<short>()` plus `CK_<Table>_<Enum>` listing allowed values; never renumber existing members |
| `decimal` money/quantities | `numeric(p,s)` | Always `HasPrecision(p, s)`, e.g. `(19,4)` for money |
| `bool` | `boolean` | Not null, with a default when added to an existing table |
| value objects | columns on the owner's table | `ComplexProperty` (columns `<Property>_<Member>`); not `OwnsOne`/`OwnsMany`, which become separate tracked entries that soft delete deletes; `jsonb` only for genuinely schemaless data |

- Required: mark every non-nullable reference type `IsRequired()`; nullable columns must be
  nullable in C# too.
- Audit columns from `Entity`/`SoftDeletableEntity` (`CreatedAt`, `CreatedBy`,
  `UpdatedAt`, `UpdatedBy`, `IsDeleted`, `DeletedAt`, `DeletedBy`): map them on every
  table that inherits them; `*By` columns are `HasMaxLength(64)` and stay nullable. See
  "Base classes and the audit interceptor" below for who sets them.
- Soft delete: add `HasQueryFilter(x => !x.IsDeleted)` and make unique indexes filtered:
  `.HasFilter("\"IsDeleted\" = false")`. Delete through a domain method that calls
  `MarkDeleted()`, never `DbContext.Remove()` or `EfRepositoryBase.RemoveEntity()` (see
  below).
- Concurrency: aggregates that can be edited concurrently get
  `public uint Version { get; private set; }` mapped with `.IsRowVersion()` (Npgsql maps it
  to the `xmin` system column, so no migration column and no manual bumping).
- Tenancy: when the spec marks an entity as organization-owned, it has
  `OrganizationId uuid NOT NULL`, and every index used by queries starts with
  `OrganizationId`.
- Index every foreign key column and every column a spec'd query filters or sorts on.
- Delete behavior is explicit on every relationship (`OnDelete(DeleteBehavior.Restrict)` by
  default). `Cascade` only for children of a hard-deleted (`Entity`) aggregate, stated in
  the spec; never under a `SoftDeletableEntity` principal.

### Base classes and the audit interceptor

Module entities inherit one of the SharedKernel bases; nothing else in the platform is a
base for persisted entities.

| Base (`Shipwise.SharedKernel.Abstractions.Domain`) | Columns it brings | Use for |
|---|---|---|
| `Entity` (`Entity<Guid>`) | `Id`, `CreatedAt`, `CreatedBy`, `UpdatedAt`, `UpdatedBy` | Entities that are hard deleted |
| `SoftDeletableEntity` | the above plus `IsDeleted`, `DeletedAt`, `DeletedBy` | Entities that are soft deleted |
| none | - | `OutboxMessage`, `InboxMessage`, `IdempotencyRecord` are platform-owned: never inherit, remap or extend them |

Rules (each was checked against the real interceptor on a throwaway model):
- Ids: constructors pass `Guid.CreateVersion7()` to `base(id)`; the parameterless
  constructor is private and exists only for EF. With `ValueGeneratedNever()` a skipped id
  is saved as `Guid.Empty` and the second insert fails on the primary key.
- Never redeclare, hide or assign the audit properties in handlers. `CreatedAt` is set when
  the entity is constructed; `AuditSaveChangesInterceptor` sets `CreatedBy` on insert,
  `UpdatedAt`/`UpdatedBy` on every update, and `DeletedAt`/`DeletedBy` on soft delete. With
  no signed-in user (MigrationRunner, workers, seeding) the `*By` values are null.
- Soft delete only through the domain: expose a method that calls `MarkDeleted()`, then
  save. Verified: the root becomes one UPDATE with all audit columns set and children stay
  untouched. `DbContext.Remove()` on a soft-deletable root is wrong: the interceptor turns
  only the root into an UPDATE, while owned types and loaded `Cascade` children are still
  hard deleted, and with `Restrict` the `Remove()` call throws. Children that must disappear
  with their parent are `SoftDeletableEntity` too and the domain method marks them.
- Register the interceptor per scope, because it resolves the scoped
  `ICurrentUserProvider`. Verified: a singleton registration throws "Cannot resolve scoped
  service ... from root provider".
  ```csharp
  services.AddScoped<AuditSaveChangesInterceptor>();
  services.AddDbContext<OrganizationsDbContext>((sp, options) => options
      .UseNpgsql(connectionString, npgsql => npgsql.MigrationsHistoryTable("__EFMigrationsHistory", "organizations"))
      .AddInterceptors(sp.GetRequiredService<AuditSaveChangesInterceptor>()));
  ```
- `ExecuteUpdate`/`ExecuteDelete` skip SaveChanges interceptors, so they write no audit
  columns and perform hard deletes. Do not use them on audited or soft-deletable tables
  unless the code sets the audit columns itself and the spec says why.
- Times: use `DateTimeOffset.UtcNow` (or `TimeProvider`); Npgsql writes
  `timestamp with time zone` only for offset zero, so `DateTimeOffset.Now` fails at save.
- Row version vs revision: the concurrency property is `uint Version` (verified: Npgsql
  maps it to `xmin` and creates no column). If an aggregate also needs an event revision
  for the outbox (`OutboxMessage.AggregateRevision`, `IDomainEvent.Version`), name that
  persisted `long` property `Revision`.
- A dependent with a required navigation to a soft-deletable principal gets the same
  query filter (or an optional navigation); EF warns otherwise.
- Reliability tables live in the fixed `reliability` schema of the module's own database,
  which is why modules never share a database.

## 4. Commands

Use the pinned tool (`dotnet ef`, EF Core 10). Never point design-time tools at a shared or
production database. The design-time factory reads `SHIPWISE_DESIGN_POSTGRES` and falls
back to the local compose database; it never contains real credentials.

```powershell
$m = 'Organizations'   # module
$infra = "src/Modules/$m/Shipwise.$m.Infrastructure"

# Add (one migration per task per module, in its own commit)
dotnet ef migrations add AddOrganizationSlug --project $infra --startup-project $infra `
  --context "${m}DbContext" --output-dir Persistence/Migrations

# Prove the model and migrations agree (must print "No changes")
dotnet ef migrations has-pending-model-changes --project $infra --startup-project $infra --context "${m}DbContext"

# Script for review: give it to the reviewer in the handoff report
dotnet ef migrations script <PreviousMigration> AddOrganizationSlug --idempotent `
  --project $infra --startup-project $infra --context "${m}DbContext"

# Undo a migration that has NOT been pushed
dotnet ef migrations remove --project $infra --startup-project $infra --context "${m}DbContext"
```

Applying migrations: only `Shipwise.<Module>.MigrationRunner` (or its idempotent script in
deployment) runs `Database.MigrateAsync()`. API and Worker hosts never migrate on startup,
and nothing calls `EnsureCreated` against a module database.

## 5. Safe change rules

1. Never edit, rename or delete a migration that has been pushed. Fix forward with a new one.
   Before it is pushed, `migrations remove` and re-add instead of editing generated code.
2. Model snapshot conflicts: never hand-merge `<Module>DbContextModelSnapshot.cs`. Pull the latest
   `main`, remove your migration, re-add it.
3. Review the generated `Up` and `Down` code before committing. EF turns renames into drop +
   add: replace them with `RenameColumn`/`RenameTable` so data survives.
4. Destructive or locking changes use expand/contract across separate releases and
   need the spec to say "destructive: yes" plus human approval:
   - drop a column/table: stop reading and writing it first, drop it in a later release;
   - rename: add the new column, backfill, switch code, drop the old one later;
   - add `NOT NULL` to an existing column: add nullable, backfill with `migrationBuilder.Sql`,
     then make it required;
   - narrow a type or length: verify existing data fits in the migration first.
5. New `NOT NULL` columns on existing tables need a default or a backfill in the same
   migration.
6. Large-table indexes: `migrationBuilder.Sql("CREATE INDEX CONCURRENTLY ...",
   suppressTransaction: true)` in its own migration.
7. Raw SQL in migrations: quote identifiers, keep it idempotent where possible, and explain
   why in a comment.
8. Implement `Down` for every non-destructive migration. Production rollback is a new
   forward migration, not `Down`.
9. Seed data: `HasData` only for fixed reference data (with fixed GUIDs). No business,
   demo or environment-specific data in migrations.
10. Generated migration files are exempt from style fixes; do not reformat them.

## 6. Required tests per module

- A unit test asserting the model has no pending changes:
  `Assert.False(context.Database.HasPendingModelChanges())` (no database needed).
- An infrastructure test (`[PostgreSqlFact]`, runs in CI) that applies all migrations to
  an empty database with `MigrateAsync()` and exercises one write and read per new table.
- Tests for every check constraint and unique index the migration adds (violations fail).
- For each soft-deletable aggregate: deleting through the domain method leaves one row with
  `IsDeleted`, `DeletedAt` and `DeletedBy` set, hides it from queries, and leaves children
  untouched.

## 7. Change checklist (author checks before committing, reviewer rechecks)

- [ ] Matches the spec's "Database design" exactly (tables, columns, types, indexes,
      constraints, migration names); any deviation went back to the spec first
- [ ] Entities inherit `Entity` or `SoftDeletableEntity`, pass a v7 id to `base(id)`, never
      assign audit columns, soft delete via `MarkDeleted()` (no `Remove()`), use
      `ComplexProperty` for value objects, and the interceptor is registered per scope
- [ ] Migration name follows section 2 and describes the change
- [ ] Table, index, constraint names and column types follow sections 2 and 3
- [ ] `has-pending-model-changes` prints "No changes"
- [ ] Idempotent SQL script given to the reviewer; renames are renames, not drop + add
- [ ] Destructive change? Spec says so and a human approved; expand/contract followed
- [ ] Indexes for foreign keys, tenancy and spec'd queries; delete behavior explicit
- [ ] Tests from section 6 added and passing in CI (infrastructure tests not skipped)
- [ ] No pushed migration was edited; snapshot regenerated, not hand-merged
